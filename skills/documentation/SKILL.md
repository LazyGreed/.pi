# Documentation

Document intent and non-obvious decisions, not a second copy of executable code. Prefer authoritative sources in this order: code/tests/schemas/config, runtime evidence, decisions, then explanatory prose. Keep README practical, AGENTS durable, ADRs for meaningful rationale, and specs focused on behavioral acceptance.

Write with specific nouns, constraints, and observed evidence. No 'robust', 'seamless', 'best-in-class', generic opening paragraphs, inflated adjective stacks, fake certainty, or template sections that add no decision value. No em dash by default. Preserve facts, names, negation, IDs, commands, dates, and qualifications while editing. Distinguish observed, inferred, and unverified claims.

For specs use `references/specs.md`. For documentation audit and unslop rules use `references/editing.md`. Never create documents or tests merely because a process checklist mentions them.
